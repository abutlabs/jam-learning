# Put your client on a jamswap net

jamswap never talks to a client's internals. The exchange reaches the chain only through
[JIP-2](https://github.com/polkadot-fellows/JIPs), the node RPC, and each net is generated
from a list of which client runs each validator. So joining is mostly a question of
standards your node may already meet.

## What your node needs

1. **JAMNP-S**, to be a validator beside the other clients on the net.
2. **A JIP-4 chain spec and a JIP-5 dev key by index**: every net mints one genesis and
   gives each validator its own key (for example `--chain spec.json --dev-validator 3`).
3. **JIP-2 on a WebSocket**, conventionally port 19800, serving what the exchange and its
   deploy call: `parameters`, `bestBlock`, `finalizedBlock`, `parent`, `stateRoot`,
   `listServices`, `serviceData`, `serviceValue`, `servicePreimage`, `serviceRequest`,
   `workPackageStatus`, `submitWorkPackage`, `submitPreimage`. Optional: `syncState` and
   `statistics`, which the dashboards read.
4. **A Bootstrap service (id 0)** if the exchange should deploy at runtime; a net without
   one seeds the service into genesis.
5. Optional: **JIP-3 telemetry** (`--telemetry HOST:PORT`) for the Block life dashboards.

## Check your node

Run your node on its own dev chain, then from the jamswap directory:

```sh
python3 offchain/jip2_check.py ws://<your-node>:19800
```

It calls every method above: the reads for real at your best block, the two submissions
with no arguments so nothing reaches the chain. A node that can run jamswap looks like this
(lasair and PolkaJam both do):

```
ok    parameters         served
ok    bestBlock          served
...
ok    submitWorkPackage  served (refused the empty probe, -32602)
ok    submitPreimage     served (refused the empty probe, -32602)
ok    syncState          served  (optional)
ok    statistics         served  (optional)
Bootstrap service (id 0): present, runtime deploy possible
jamswap can run on this node
```

A missing method shows as `MISS` and the last line lists what jamswap still needs.

## Add it to a net

Nets are generated by `nets/netgen.py` from the profiles in `nets/profiles.py`. A client is
one adapter function that returns its node's compose service. PbnJam's is this:

```python
def svc_pbnjam(n, p, ctx):
    s = {"image": "${PBNJAM_IMAGE:-%s}" % profiles.PBNJAM_IMAGE}
    s.update(_node_common(n))
    s["command"] = ["--chain", "/shared/spec.json", "--dev-validator", str(n["index"]),
                    "--rpc-port", str(n["rpc"]), "--temp"]
    s["volumes"] = ["shared:/shared:ro"]
    s["ports"] = [_udp(n), _rpc(n)]
    return s
```

Write yours the same way and register your client in four small tables: its name in
`CLIENT_ALIASES` (`nets/genesis.py`), and in `nets/netgen.py` its node-name prefix in
`SERVICE_PREFIX`, its adapter in `ADAPTERS` and its dashboard labels in `OBS_KINDS`. Then
add a profile, for example three PolkaJam validators and three of yours with the exchange:

```python
"pj-yours": dict(clients="pj,pj,pj,yours,yours,yours", net=<unused 1..99>,
                 finality="grandpa", dex=True, about="3 PolkaJam : 3 yours + the DEX"),
```

Then `./dex gen`, `./dex up NET=pj-yours` and `./dex soak NET=pj-yours 600`, and open an
issue in [jamswap](https://github.com/abutlabs/jamswap/issues) with what you saw: the
verdict, the dashboards, the logs.

## How your client is treated

As a black box: jamswap runs your published image and reads its public I/O, and any
divergence is judged against the Graypaper, JAMNP-S and the JIPs, never against another
client's behaviour. jamswap is a JAM *service*, not an implementation, so running it or
reading its code is outside the JAM Prize's clean-room rules, which cover implementation
code. Adapters for JavaJAM and PbnJam already exist (`pj-javajam`, `pj-pbnjam`) from an
earlier round; those nets have not been run lately, so they are the easiest place to
start.
